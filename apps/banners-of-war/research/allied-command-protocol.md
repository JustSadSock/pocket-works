# Allied Command — authority protocol, not yet public
The roster module is intentionally not routed from BannersMatchRoom until per-member information views/replay capture, room persistence, identity-bound invitations, real browser interface, and 2–4-client integration checks are complete. It is an executable domain layer, not a playable feature. It uses immutable banners-engine-v1 and its order validation. Existing duel state and routes are untouched.

Formats reserve 2vAI, 2v1, 2v2 and 3vAI seats. A captain owns the undelegated regiments; subordinates hold disjoint subtrees of the established four-level hierarchy. Ancestor orders spanning another player's scope are rejected rather than resolved by arrival order. General intent can be communicated separately as a typed marker. A captain may reassign a subtree or transfer leadership only before sealing; outstanding drafts on the side are invalidated. Explicit AI delegation is restricted to the captain and applies the same order validator. A deadline can seal latest drafts for disconnected users. Historical markers are directed; no remote battle observation is synthesized. In standard rooms, shared markers are supported by the model, but initial assignment requires an actual hierarchy; standard room adapter is not complete.

The current tests use real v1 historical scenario states, exercise all four seat formats, validate scope and replay/round transition, and execute a combined historical-command round. They do not prove network security or reconnect behaviour for Allied Command. Future room integration must use opaque seat IDs, bind actors to Pocket ID server-side, persist authority changes atomically and version per-player frame visibility; no reuse of side-wide replay for subordinate clients without a disclosure review.
