# Архитектура PocketNet и протокол будущей игры

Сверено с исходниками 2026-10-17. Исходники — главный источник текущих ограничений, а не предполагаемые «тики».

## Нынешний сервер
Cloudflare Worker + единый хаб `PocketNetHub` на SQLite Durable Object с hibernatable WebSockets. Игровое сообщение попадает в `run(task)` с общей Promise-очередью; сервер вызывает `mod.onMessage`, валидирует события, сохраняет room state в SQLite, рассылает события. Постоянного авторитетного цикла в 20/60 Hz **нет**. У примера «НАТЯЖЕНИЕ» пользовательские команды подаются примерно раз в 65 ms и снимки выдаются с интервалом ≥55 ms, однако это локальное решение, **не SLA** сервера.

Кодовые ограничения (`pocketnet/hub.mjs`): 32 комнаты, 48 WebSocket подключений, глобально до 8 игроков, 16 KiB входящий packet, 30 сообщений/с с одного socket, до 32 игровых событий от одной команды, 256 KiB room state и стандартного game event (исключение для «Замазки» не распространяется на нас). Комнаты неактивные 30 минут удаляются. Глобальные квоты Cloudflare Workers Free меняются; перед релизом измерять actual usage, не полагаться на эту цифру как гарантию.

## Запрещенная схема
Нельзя синхронизировать pointermove, частицы, физику или звуковые кадры каждого участника. В текущей логике `game_message` сохраняет комнату даже на не изменяющихся input/sync событиях и переустанавливает alarm; high-frequency commands плохо масштабируются по строковым записям, очереди и CPU. Нельзя использовать PocketLAN — режим неактивен.

## Целевая схема
Клиент немедленно рисует локальные жесты и анимации. Передает только:
- `prepare_op`: конечный выбор/операция станции, revision и idemKey;
- `send_sign`: одно структурированное сообщение/указатель;
- `commit_role`: зафиксировать завершение своей станции;
- `retract_role`: отменить до lock;
- `cast_dogma_vote`: выбрать предложенный догмат;
- `sync`: запрос полного безопасного пользовательского представления;
- `time_ping`: редкая оценка смещения часов.
Сервер в одном обработчике принимает/отвергает команды и создает маленькие delta events. Клиенты применяют revision; при пропуске — sync. Объекты передаются идентификаторами и конечными слотами, не координатами каждого кадра.

## Политика таймеров
`phaseEndsAt` — серверный epoch milliseconds, UI использует RTT corrected clock и никогда не завершает фазу без authoritative transition. Переход происходит при получении очередной команды/редкого pulse после дедлайна. Deadline grace 1.5–3s на последнюю подтвержденную команду, откалибровать тестами. Alarm не использовать как 60 Hz heartbeat. При disconnect сервер хранит seat, last committed choice и phase; после reconnect пересылает snapshot.

## Безопасность: блокер, требующий отдельного platform PR
Текущий путь `create_room`/`join_room` отправляет `state: room.state` в `room_joined`. Если записать туда тайные сведения, их получит любой участник. Событие `to: player.id` помогает скрыть рассылку, **но не защищает исходный снапшот**. До исправления транспортного контрактa нельзя полагаться на приватность роли. Возможные решения:
A. Обобщенное `module.viewForPlayer(state, player)` в хабе при создании, переподключении, join и sync + запрет утечки в других metadata.
B. Разделить публичное/приватное состояние хранения, приватное не включать в `room.state` клиента, отдать через targeted events по авторизованному id.
Изменение PocketNetHub — отдельно помеченный `platform-change` PR с регрессиями других игр. В P2 без этого протокола никакой секретной информации нет.

## Идемпотентность и гонки
Команда включает `{matchId,phaseId,actionId,clientSeq,baseRevision,body}`. Сервер отклоняет чужую фазу, повторный `actionId` возвращает прежний ack, проверяет ownership станции и conflict revision. Действия независимых станций коммутативны. Пакет `state_delta` несет monotonic `revision`, `eventId`, `serverNow`.

Пример `prepare_op`: `{type:'prepare_op',actionId:'u42-7',phaseId:'rite-3',baseRevision:12,body:{station:'sacristy',itemId:'goose',slotId:'altar-2'}}`. Вся генерация результата — на сервере; seed иллюстрирует чудо одинаково на клиентах.

## Бюджет (целевые числа, не лимиты платформы)
На 5 человек и 15 минут: <1500 команд за матч с пиками ≤5 команд/с с клиента на коротком отрезке; обычный темп ≤1 команда/с с клиента, средний значительно ниже; state <64 KiB; delta event обычно <2 KiB; целевой soft cap <4 событий/команду. Не гонять `sync` при каждом UI-тапе.

Важное примечание: фактическое число записей выше числа команд, поскольку в текущем хабе `persist(room)` сопровождается `setAlarm`. Оптимизация no-op сообщений и dirty-state должна быть отдельным platform PR **после профилирования**, с тестами обратной совместимости.

## Голосовая связь
PocketNet не содержит WebRTC media/Opus/TURN; голосовой чат **не часть MVP**. Связь организована фиксированными игровыми сигналами; Discord или голос рядом допустимы, но не требуются.

## Источники и точки внедрения
- `pocketnet/hub.mjs`: `run`, `webSocketMessage`, `persist`, `emit`, `ensureAlarm`.
- `shared/capabilities/net.js`: `sendGame`, `room_joined`, `reconnect`.
- `apps/natyazhenie/server/module.ts`: обработка input и snapshot.
- `apps/zamazka/server/module.ts`: private targeted events, time ping и deadlines.
- `docs/POCKETNET-CLOUDFLARE.md`: опубликованный контракт облачного сервера.

## Нагрузочные проверки перед выпуском
2/3/5 устройств, две параллельные комнаты, 150/300/600 ms RTT, 3% packet loss, короткий disconnect и reconnect, reorder/duplicate actionIds, фазы на 0:00, одновременное `commit`. Метрики: p50/p95 ack, queue wait, writes/room, events/room, полный матч без divergence. Без этих результатов нельзя утверждать, что «сервер работает быстро».
