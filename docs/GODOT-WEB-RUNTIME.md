# Godot Web Runtime

Pocket Works supports Godot as an optional build runtime for games that materially benefit from a full scene graph, skeletal animation, physics, navigation, particles or complex 3D authoring.

Godot is not a new manual development environment for Pocket Works. Repository agents author the project as text, GitHub Actions runs the pinned editor headlessly, and Cloudflare continues to publish only static browser output.

## Architecture

~~~text
repository agent
    |
    +-- apps/<slug>/project.godot
    +-- apps/<slug>/source/*.gd, *.tscn, *.tres
    +-- apps/<slug>/assets/**
    +-- apps/<slug>/asset-forge/**       optional Blender source
                |
                v
        GitHub Actions
        Godot 4.7.2 headless
                |
                v
        apps/<slug>/web/**
        HTML + JS loader + WASM + PCK
                |
                v
        Pocket Works production assembly
                |
                v
        Cloudflare Workers static assets
~~~

Cloudflare never installs Godot. A production deployment must consume a committed, already-generated web directory.

## Runtime selection

Use Quick or Enhanced by default when browser-native code is sufficient.

Use Godot when the game has a meaningful need for several of the following:

- character rigs and animation state machines;
- non-trivial 3D physics and collision;
- navigation and agent movement;
- complex scene hierarchies;
- authored particle systems;
- environment/level composition that benefits from a game-engine scene model;
- repeated 3D gameplay systems that would otherwise recreate engine infrastructure in Babylon/TypeScript.

Godot is not chosen for prestige or because a game is merely 3D. Babylon/WebGPU remains a strong browser-native path.

## Create an application

~~~bash
npm run new:app -- my-game --runtime=godot --preset=godot-web --orientation=landscape
~~~

The generated application owns:

~~~text
apps/my-game/
├── app.config.json
├── project.godot
├── export_presets.cfg
├── source/
│   ├── main.tscn
│   ├── main.gd
│   └── pocket_works.gd
├── icons/
│   └── icon.svg
├── assets/
│   └── ...
└── web/
    └── generated by GitHub Actions
~~~

Agents edit source files. The web directory is generated output and must not be hand-authored.

## Browser target

Pocket Works currently pins Godot 4.7.2 for deterministic CI exports.

The Web preset is intentionally conservative for iPhone/Safari:

- Compatibility renderer;
- WebAssembly export;
- thread support disabled;
- extension support disabled;
- Godot PWA generation disabled because Pocket Works owns the manifest, Service Worker, update contract and release fingerprinting;
- GDScript as the default scripting language.

Do not introduce C# or a GDExtension into a Godot Web app without a separate platform decision. Browser compatibility and build requirements differ from the normal desktop Godot path.

## PocketWorks bridge

The PocketWorks autoload in source/pocket_works.gd is the runtime boundary between Godot and the browser shell.

The baseline bridge provides:

- exit_to_launcher();
- publish_test_state(state);
- storage_set(key, value);
- storage_get(key, fallback);
- storage_remove(key);
- set_document_title(title).

Storage keys are always namespaced by the app storageNamespace from app.config.json.

publish_test_state writes window.__AI_TEST_STATE__ so Playwright and repository agents can inspect real game state instead of relying only on screenshots.

Add app-specific logic in the app. Add a new shared bridge capability only when at least two real Godot apps need the same stable abstraction.

## Blender Asset Forge

Blender remains the preferred deterministic authoring backend for important generated 3D assets.

A Godot app may keep Blender Python under asset-forge/ exactly like a Babylon app. Blender generates app-local GLB assets; Godot imports those resources during its headless export.

Typical sequence:

~~~text
agent edits Blender Python
        |
Blender Asset Forge
        |
generated GLB committed to app branch
        |
Godot Web Runtime workflow
        |
generated Web export committed to app branch
~~~

The Godot workflow also reacts to app-local generated asset changes, so a Blender-generated GLB can naturally trigger a fresh Godot export.

## GitHub Actions flow

.github/workflows/godot-web-runtime.yml performs four jobs inside one isolated runner:

1. restore or download the pinned Godot editor and official export templates;
2. verify the official SHA-512 checksums;
3. smoke-export apps/_godot-template;
4. export affected registered Godot apps and validate the result.

On a normal feature-branch push, changed Godot applications are exported and apps/<slug>/web is committed back with the marker [godot-export].

That marker prevents an infinite workflow loop.

Before downloading or running Godot, the workflow runs the validator in source-only mode. This checks project structure, Web export settings, the PocketWorks bridge and required app source without requiring the previously committed `web/**` output to already match a just-bumped app version. The temporary `godot-ci-smoke` export is validated with `--app godot-ci-smoke` so an intentionally stale committed export from the real app being rebuilt cannot block the smoke fixture. After the affected app export completes, the normal full validator runs and enforces generated Web metadata/freshness.

For pull requests, the workflow performs the same deterministic build and fails if the committed web output differs from the generated result. PR and main runs also install the normal repository dependencies, rebuild Enhanced apps, assemble dist-site and run validate:site so the generated Godot payload is checked inside the same production package Cloudflare will serve.

Feature-branch push runs intentionally skip that full repository integration build and focus on source validation, Godot export and app-local output generation. This keeps the edit/export loop materially lighter while PR/main remains the production boundary.

The GitHub Actions cache stores the editor and export templates so later builds avoid repeatedly downloading the large Web toolchain.

## Production assembly

npm run deploy:site does not invoke Godot.

Cloudflare Workers static assets have a hard 25 MiB per-file upload limit. Official Godot Web templates can exceed that limit even with threads/extensions disabled. Pocket Works therefore applies a transport-only packaging step during `prepare:site`: oversized Godot `.wasm` files are split into deterministic 16 MiB parts inside `dist-site`. The production HTML injects a tiny bootstrap before the Godot loader that intercepts only the original WASM request, downloads the parts in parallel, and exposes them back to Godot as one normal `application/wasm` byte stream.

The public Godot contract remains unchanged: the engine still asks for `index.wasm`, progress is measured against the original byte size, and there is no HTTP `Content-Encoding` layer between Safari and `WebAssembly.instantiateStreaming()`. This avoids the iOS/WebKit failure mode where compressed transfer bytes can diverge from Godot's expected uncompressed size or leave streaming compilation unresolved.

The committed `apps/<slug>/web/**` export always remains the canonical unsplit Godot output. Chunking exists only in the disposable production directory. `validate:site` concatenates every production chunk and compares it byte-for-byte with the committed WASM, verifies the Service Worker precaches the parts for offline launch, and rejects any physical asset still larger than 25 MiB.


For a Godot application, scripts/prepare-site.mjs:

1. requires apps/<slug>/web/index.html to exist;
2. copies only the generated Web output plus app.config.json;
3. stamps the normal Pocket Works release metadata and fingerprint;
4. leaves project.godot, source/, Blender source and other authoring files out of dist-site.

This keeps Cloudflare deployment fast and deterministic.

## Offline and updates

Godot's built-in PWA export is disabled. scripts/build-godot.mjs generates the Pocket Works-owned manifest and Service Worker instead.

In production, the release guard is the single owner of Service Worker registration and always uses the stable `./sw.js` script URL with `updateViaCache: 'none'`. Release version and fingerprint identity live in Pocket Works release metadata (`release.json`, stamped HTML metadata and the worker's own update info), not in Service Worker URL query parameters. The Godot HTML shell keeps a fallback registration only for direct/generated previews where the production release guard is absent. Do not create competing registrations for the same scope: WebKit can reject script-URL churn as an AbortError/access-control failure.

The generated worker:

- caches the Godot HTML/JS/WASM/PCK payload and icon;
- caches the shared release guard;
- uses an app-owned cache prefix;
- supports GET_UPDATE_INFO and SKIP_WAITING;
- never deletes another application's caches;
- resolves release query parameters with ignoreSearch so Pocket Works fingerprint stamping remains offline-safe.

## Generated build marker

Each web export includes pocketworks-build.json with:

- runtime;
- engine;
- pinned engine version;
- app slug and release version;
- source fingerprint.

This makes a stale export detectable without requiring the Godot editor during normal Cloudflare production assembly.

## CI and local commands

Source-only validation does not require Godot:

~~~bash
npm run validate:godot
npm run validate:all
~~~

If Godot 4.7.2 and its Web export templates are installed locally:

~~~bash
GODOT_BIN=/path/to/godot npm run build:godot -- --app my-game
~~~

Normal repository-agent work does not require a local Godot installation; GitHub Actions is the canonical exporter.

## Current trade-off

Runtime v1 uses a full isolated Godot Web export per application. This favors independent apps, deterministic rollback and simple offline ownership, at the cost of duplicating the engine WASM between Godot games.

Do not introduce a shared Godot engine/PCK loader until real repository size or network measurements justify the additional coupling. If that threshold is reached, treat engine deduplication as a platform change rather than an app optimization.
